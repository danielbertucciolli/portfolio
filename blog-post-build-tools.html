Por que abandonei build tools em projetos pequenos

28 jun 2026 · 6 min de leitura
TailwindVanilla JSFerramentas

Todo projeto pequeno chega numa encruzilhada: montar uma esteira completa de build — bundler, transpiler, linter, hot reload — ou simplesmente abrir um arquivo HTML e começar a escrever. Depois de alguns anos escolhendo sempre a primeira opção "porque é o correto", comecei a questionar se isso realmente valia o tempo em projetos que não precisavam de nada disso.

O problema que build tools resolvem (e o que custam)

Bundlers existem para resolver problemas reais: dividir código em pedaços menores, otimizar assets, permitir imports entre arquivos, transformar sintaxes modernas para navegadores antigos. O problema é que esse valor só aparece a partir de um certo tamanho de projeto — e a maioria dos sites institucionais, landing pages e protótipos nunca chega nem perto disso.

Um site institucional típico raramente passa de 3-4 telas e um punhado de interações. A complexidade do build costuma superar a complexidade do próprio site.

Quando o projeto é pequeno, a esteira de build vira a parte mais complicada do processo: configurar o bundler, resolver conflitos de versão, esperar o build terminar antes de ver qualquer mudança. Isso rouba tempo do que realmente importa — o design, o conteúdo e os detalhes que o cliente vai perceber.

Nem todo projeto pequeno precisa de uma esteira de build. Às vezes ele só precisa funcionar.

A alternativa que uso hoje em boa parte dos projetos: um único arquivo HTML, Tailwind via CDN e JavaScript puro. Sem package.json, sem node_modules, sem passo de build. Abre o arquivo, edita, salva, atualiza a página.

index.html
1<!DOCTYPE html>
2<html lang="pt-BR">
3  <head>
4    <script src="https://cdn.tailwindcss.com"></script>
5  </head>
6  <body class="bg-slate-900 text-white">
7    <h1 class="text-3xl font-bold">Hello, sem build!</h1>
8  </body>
9</html>

Isso já roda em qualquer navegador moderno, sem transpileração e sem instalar nada. Para landing pages, mockups de cliente e protótipos, essa simplicidade vale mais do que a otimização que um build traria.

Onde isso realmente compensa

Uso essa abordagem principalmente em três cenários: mockups para aprovação de cliente (onde velocidade de iteração importa mais que performance final), sites institucionais pequenos que não vão crescer muito, e componentes de referência — como a biblioteca de UI que mantenho no tema GitHub Dark, pensada justamente para ser copiada e colada sem depender de nenhuma ferramenta.

A CDN do Tailwind carrega mais CSS do que um build otimizado com purge. Para uma landing page isso é irrelevante; para uma aplicação grande, não é.

Quando isso não funciona

Essa abordagem tem limite, e é importante ser honesto sobre isso. Aplicações com estado complexo, várias páginas com roteamento, times grandes trabalhando no mesmo código ou qualquer coisa que precise de TypeScript, tree-shaking real ou testes automatizados — tudo isso ainda pede uma esteira de build de verdade. A ideia não é abandonar ferramentas, é escolher a ferramenta certa para o tamanho do problema.

No fim, a pergunta que uso pra decidir é simples: esse projeto vai crescer a ponto de a esteira de build se pagar? Se a resposta for não, um arquivo HTML bem organizado resolve — e resolve mais rápido.
